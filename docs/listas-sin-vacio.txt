# Colecciones que se dibujan sin estado vacío (#588).
#
# Esta lista es un TRINQUETE, no una lista de tareas: la guarda falla si
# aparece una colección nueva sin `EstadoVacio`, y falla pidiendo bajar la
# marca si una lo estrena y nadie la saca de acá. No afirma que este estado
# esté bien — afirma que no empeore y que se vea cuando mejora.
#
# La unidad es la COLECCIÓN, no el componente, y por eso este número es mayor
# que el del issue: #588 contó componentes, y un componente puede dibujar tres
# listas o ninguna. Contar componentes hacía parecer que faltaban 22 cuando
# faltan 41 vacíos y sobran 10 componentes que no son listas.
#
# Qué cuenta como «se dibuja una colección»: un `.map` dentro de llaves de JSX
# sobre un arreglo del componente, más una de dos señales —que el autor ya
# escribió la rama de vacío (`length === 0`), o que no la escribió y entonces
# es peor—. Lo que el `map` DEVUELVE recorta los menús y desplegables; lo que
# el `map` contiene no recorta nada, porque una lista con edición en línea
# tiene controles en cada fila y sigue siendo una lista.
#
# Se regenera con:  node scripts/listas-sin-vacio.mjs --escribir
# Y sin argumentos muestra qué cambió.
#
# ## Bajó de 34 a 32 el 14-10, sin tocar ninguna lista (#788)
#
# `evaluaciones` y `horarios-de-atencion` salieron de acá al migrar a
# `useCarga`, y no porque se les escribiera un estado vacío: ya lo tenían. Lo
# que las tenía listadas era la AMBIGÜEDAD — la colección en `null` significaba
# «cargando o vacío» según por dónde se hubiera llegado, y el escáner no puede
# distinguir una rama de vacío que además cubre el cargando. Con los cinco
# estados nombrados, `null` dejó de significar dos cosas.
#
# Vale anotarlo porque explica cómo se vacía esta lista de verdad: de las 32
# que quedan, la mayoría no le falta el vacío, le falta que su carga no sea
# ambigua.
#
# Las que NO son colecciones —transcripciones, resultados de búsqueda,
# sublistas de una ficha— viven en `packages/core/tests/listas-sin-estados.test.ts`
# con su motivo, porque ahí el porqué es información que no está en el código.
#
# ## Un punto ciego, medido el 13-10 (#584)
#
# La guarda escanea `apps/web/components` y `packages/ui/src/react`, y busca
# arreglos DEL COMPONENTE. Una lista cuyos datos vienen de `apps/web/lib` y se
# dibujan con `algo.propiedad.map(...)` no la ve: no es un arreglo del
# componente ni vive en una raíz escaneada.
#
# Se descubrió al mover las sugerencias del Agente General del navegador al
# servidor: la lista fija de `lib/donde-estoy.ts` llevaba semanas dibujándose
# sin estado vacío y nunca figuró acá. Al pasar a ser estado del componente,
# apareció — o sea que este número subiendo de 35 a 36 no es el producto
# empeorando, es la guarda viendo algo que antes no veía.
#
# Cuántas más hay escondidas por esa puerta: no está medido.
#
# ## Y no todas las que figuran pueden estar vacías (medido el 14-10)
#
# La guarda cuenta colecciones que se dibujan SIN estado vacío, y eso es
# mecánicamente cierto. Lo que no puede saber es si el vacío es ALCANZABLE.
#
# `preferencias-avisos.tsx#prefs` es el caso claro: el servidor hace
# `NOTIFICATION_TYPES.map(...)` sobre una lista fija del código
# (`notifications.ts:162`), así que devuelve una fila por tipo de aviso
# SIEMPRE. Un `prefs` vacío solo pasaría si el catálogo quedara vacío, y si eso
# pasara el problema no sería el estado vacío. Escribirle uno sería una
# pantalla que nadie va a ver nunca, y haría creer que el caso existe.
#
# De las 35, **24 ya distinguen cargando de vacío** y están acá solo por no
# usar el componente `EstadoVacio`; **11 tienen el pixel ambiguo**.
#
# Antes de escribirle un vacío a cualquiera de esas once, conviene preguntarse
# si puede estar vacía. Miré tres y **solo una lo necesitaba**:
#
#  - `embudos.tsx#pipelines` — SÍ. Con cero embudos se veía el título y nada
#    más: el formulario de «Agregar una etapa» vive dentro de cada tarjeta, así
#    que no había forma de crear el primero. Y es alcanzable: los embudos los
#    crea el configurador, así que un negocio nuevo que entre antes de terminar
#    el setup caía en el callejón. Arreglado.
#  - `preferencias-avisos.tsx#prefs` — NO. El servidor hace
#    `NOTIFICATION_TYPES.map(...)` sobre una lista fija del código
#    (`notifications.ts:162`): devuelve una fila por tipo SIEMPRE.
#  - `crm/ficha-contacto.tsx#campos` y `#catalogo` — NO. `campos` son las
#    definiciones de campos PROPIOS del negocio, dibujadas dentro de un
#    formulario que ya muestra nombre, RUT y el resto: con cero campos propios
#    no hay callejón, hay un formulario completo. Y `catalogo` ya está guardado
#    con `catalogo.length > 0 &&`, así que el menú de etiquetas no aparece si
#    no hay ninguna — que es lo correcto.
#
# Dos de tres hipótesis eran falsas. Vale la pena medirlo antes de escribir:
# un estado vacío para un caso inalcanzable es una pantalla que nadie va a ver,
# y peor, hace creer que el caso existe.
